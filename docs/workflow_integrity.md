# 作成・独立点検・公開の運用

通常運用の正本は本書と `AGENTS.md`。本文の正本は `prompts/entry_spec_v5.md`。
旧監査文書や保存済みrunは、新しい通常作業の要件を追加しない。

## 作成と点検を分ける

作成者は完成物のルールに沿って執筆する。辞書・用例・必要な一次資料の確認、
推敲、主要語義と構文の整理は執筆の一部として行う。作業表、候補一覧、出典台帳、
検索履歴、確認済み証明を別ファイルへ出力する義務はない。
確認できない重要事項は断定せず、未解決のまま公開しない。

本文の形式を確認した後、新規チャットまたは文脈を分離したコンテキストへ、
対象本文・完成物基準・独立点検指示を渡す。同じモデルでもよいが、作成履歴、
作成者の合格宣言、過去のレビュー判定を初回点検の入力にしない。
`simple_workflow.py --review-entry` はfront matterを除いて引渡し文を作るだけで、
LLMを起動したり、独立性を認証したり、記事の状態を変更したりしない。
ツールを利用できなくても同じ内容を手動で渡せる。

指摘は「誤り・重要な欠落」「誤解につながる説明」「任意の表現改善」を分ける。
問題数のノルマは設けない。疑わしい指摘は資料で確認し、妥当でない指摘に合わせて
正しい本文を変更しない。点検の結果や未解決事項はチャットまたはPRに簡潔に残せばよく、
固定schema・全項目の合格理由・raw保存・実行ID・hashの登録は要求しない。

## 修正と終了

全体点検は原則1回。必要な修正後は変更箇所と関連部分を確認する。
語義分割・コアイメージ・参照番号などを広く変更した場合は、その影響に応じて
確認範囲を広げる。軽微な修正や本文hashの変化だけで全面点検をやり直さない。
既存記事の局所修正は、独立点検も依頼範囲と関連部分を中心に行い、全面再作成にしない。

終了条件は「把握した重要な誤りが解消し、必要な確認が済んだこと」。
改善案が一切出ないことや、所定回数の往復を消化することではない。
同じ争点が解決しない場合は、その争点の根拠確認に絞る。確認できなければ
未解決事項として残し、合格扱いにしない。途中成果は保存して引き継ぐ。

## 状態の意味

| 状態 | checked | 意味 |
| --- | --- | --- |
| draft | false | 執筆途中 |
| review_ready | false | 本文を作成済み、独立点検待ち |
| needs_review | false | 内容上の未解決事項・未確認範囲がある |
| format_error | false | 形式エラーが残る |
| checked / final | true | 独立点検と必要な修正を終え、公開可能 |

作成だけの依頼なら `review_ready` で完了してよい。独立点検が利用できない場合も同じ。
未実施の独立点検を自己点検や依頼文生成で代用せず、その制約を報告する。
既存のchecked記事を内容変更して点検が未完了なら、作業branchの状態を下げる。
未変更の過去記事の状態や、過去のレビュー結果を一括変更しない。
CIはこの意味的な実施事実を認証しない。状態を付ける担当者の責任を明示する。

## 保存と公開

通常の必須変更は対象記事と、その記事に対応する `queue/words.csv` の行だけ。
`updated_at` と生成・修正モデルなどのメタデータを実態に合わせ、未実行のモデル名を
書かない。出力書式と `prompt_version: entry_spec_v5` は変えない。
既存データの全面整形、全語の再生成、旧監査の再束縛、完了runの新規作成は不要。
エクスポートは利用先が必要とする場合だけ既存ツールで更新する。

```sh
python scripts/validate_entry.py <記事パス>
python scripts/validate_repository.py
```

専用branchからPRを作成し、対象headのCI成功を確認する。承認範囲内でマージする。
CIの `validate` はUbuntu/Windows両方の成功を必要とする既存名を維持し、
自動テスト・記事形式・queue整合を検証する。旧監査の履歴・出所・時系列・
source-first gateは通常CIにもNotion同期にも含めない。
旧仕様の互換性テストは残すが、現存する全監査を新しい公開条件として再検証しない。

`checked` / `final` かつ `checked: true` の記事だけをNotionへ同期する。
mainへの反映とNotion同期は別々に確認する。同じ記事の連続改訂では先の同期完了を
確認し、古い版が後から上書きされないようにする。同期失敗時は対象記事の最新mainを
workflow_dispatchで再同期し、本文点検をやり直したことにしない。

## 旧工程からの切り替え

過去のrun、raw、失敗記録は不変の履歴として残す。旧工程を明示的に再開する場合は
`docs/legacy_workflows.md` を参照する。通常工程へ切り替える場合は最新本文と
未解決の具体的指摘を引き継ぎ、旧runをPASSへ変換せず、旧記録はそのまま残す。
別の監査migration、hashの更新、架空のレビュー結果は作らない。
